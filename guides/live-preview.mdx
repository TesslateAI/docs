## What is Live Preview?

The Live Preview shows your running application inside an iframe embedded in the Tesslate Studio workspace. Every change you make in the code editor or through an AI agent appears in the preview within milliseconds, thanks to Hot Module Replacement (HMR).

The preview is not a simulation. It is your actual application running inside a real container, accessed through a reverse proxy that routes traffic to the correct dev server.

## How the Preview Works

The preview is an iframe that loads a URL pointing to your project's dev server. The URL is generated differently depending on the deployment mode:

<Tabs>
  <Tab title="Docker Mode (Local Development)">
    Tesslate uses **Traefik** as a reverse proxy. Each container gets a unique URL based on the project slug and container name:

    ```
    {project-slug}-{container-name}.localhost
    ```

    For example, if your project slug is `my-app-k3x8n2` and the container is named `frontend`, the preview URL would be:

    ```
    my-app-k3x8n2-frontend.localhost
    ```

    Traefik routing is configured through labels in the dynamically generated `docker-compose.yml` file.
  </Tab>

  <Tab title="Kubernetes Mode (Production)">
    Tesslate uses **NGINX Ingress Controller** with TLS wildcard certificates. Each container gets a subdomain:

    ```
    {container-name}.{project-slug}.{domain}
    ```

    For example, on the production domain `saipriya.org`:

    ```
    https://frontend.my-app-k3x8n2.saipriya.org
    ```

    Ingress rules are created per container, and a wildcard TLS certificate covers all subdomains.
  </Tab>
</Tabs>

### Multi-Container Previews

In multi-container projects, you can preview different containers independently. The architecture graph includes BrowserPreview nodes that you can connect to specific containers. Each BrowserPreview stores its own URL path state, so you can have the frontend preview showing the login page while a second preview shows the API documentation.

<Tabs>
  <Tab title="Normal Mode">

## Hot Module Replacement (HMR)

### How It Works

HMR is a development feature provided by Vite (or your project's bundler) that updates the browser without a full page reload.

<Steps>
  <Step title="Code Changes">
    You edit a file in the editor, or an AI agent writes to the filesystem.
  </Step>
  <Step title="Dev Server Detects Change">
    The Vite dev server (or equivalent) watches the filesystem and detects the modified file.
  </Step>
  <Step title="Module Replacement">
    Only the changed module is recompiled and sent to the browser via WebSocket.
  </Step>
  <Step title="State Preserved">
    React component state, form inputs, and scroll position remain intact. Only the changed component re-renders.
  </Step>
  <Step title="Preview Updates">
    The change appears in the preview within milliseconds.
  </Step>
</Steps>

### What Triggers HMR

- **Component changes**: Editing React, Vue, or Svelte components
- **Style updates**: Modifying CSS, SCSS, or Tailwind classes
- **Asset changes**: Updating images, fonts, or other static files
- **Configuration changes**: Some config updates (these may require a full reload)

<Info>
  HMR is much faster than full page reloads because it only replaces the changed modules. This makes the edit-preview cycle nearly instant, which is especially valuable when iterating with AI agents.
</Info>

### When HMR Falls Back to Full Reload

Some changes cannot be hot-replaced and trigger a full page reload:

- Changes to the entry file (`main.tsx`)
- Modifications to `vite.config.ts` or `tsconfig.json`
- Adding or removing dependencies (requires a server restart)
- Syntax errors that prevent the module from compiling

## Responsive Design Testing

The preview panel can be resized to test different screen widths:

<Tabs>
  <Tab title="Desktop">
    Full-width preview showing the desktop layout. Drag the panel edge to adjust the width.
  </Tab>
  <Tab title="Tablet">
    Resize the preview to tablet-range widths (768px to 1024px) to test medium breakpoints and touch-oriented layouts.
  </Tab>
  <Tab title="Mobile">
    Narrow the preview to mobile widths (320px to 480px) to verify responsive behavior, mobile navigation, and touch-friendly elements.
  </Tab>

For more precise testing, open the preview in a new browser tab and use your browser's built-in responsive design tools (for example, Chrome DevTools Device Mode).

### Server Controls

From the project settings panel:

- **Restart Container**: Stop and restart a specific container's dev server
- **Restart All**: Stop and restart all containers in the project
- **View Status**: See the current status of each container
- **Port Info**: Check which port the dev server is listening on

## Port Resolution

The preview URL includes the correct port for each container. Tesslate determines the port using the `effective_port` property:

1. `internal_port` (set from TESSLATE.md or framework detection)
2. `port` (the mapped/exposed port)
3. `3000` (fallback default)

At container startup, the orchestrator also checks for a TESSLATE.md file that can override the port at runtime.

## Troubleshooting

<AccordionGroup>
  <Accordion icon="circle-xmark" title="Preview Not Loading">
    **Cause**: Dev server has not started yet, or the container is not running.

    **What to try**:
    - Wait 30 to 60 seconds for initial startup
    - Check the container status indicator
    - Restart the dev server from project settings
    - Open the preview URL in a new tab and check the browser console
    - For non-Node.js projects, try the "Ask Agent to start it" feature
  </Accordion>

  <Accordion icon="ban" title="Changes Not Appearing">
    **Cause**: HMR connection lost, or a build error prevents module replacement.

    **What to try**:
    - Check if there are syntax errors in the editor (red underlines)
    - Click the refresh button in the preview toolbar
    - Check the browser console in the preview for error messages
    - Ensure the file was saved (`Ctrl/Cmd + S`)
    - Restart the dev server if HMR is completely unresponsive
  </Accordion>

  <Accordion icon="triangle-exclamation" title="Build Error Overlay">
    **Cause**: A syntax error or type error prevents the application from compiling.

    **What to try**:
    - Read the error message shown in the overlay
    - Check the file and line number referenced in the error
    - Fix the error in the editor and save
    - Ask an AI agent to debug the issue: paste the error message in the chat
  </Accordion>

  <Accordion icon="snail" title="Slow Preview">
    **Cause**: Large bundle size, unoptimized images, or heavy computation in the render cycle.

    **What to try**:
    - Close other browser tabs to free resources
    - Optimize large images (compress or resize)
    - Check for infinite re-render loops in the browser console
    - Profile the application using Chrome DevTools Performance tab
  </Accordion>
</AccordionGroup>

## Best Practices

<CardGroup cols={2}>
  <Card title="Test After Each Change" icon="vial">
    Check the preview after each code edit or AI generation. Catching issues early is much easier than debugging a series of accumulated changes.
  </Card>
  <Card title="Use DevTools Regularly" icon="browser">
    Open the preview in a new tab periodically. Use Chrome DevTools to inspect elements, check network requests, and verify responsive layouts.
  </Card>
  <Card title="Monitor the Console" icon="terminal">
    Keep an eye on the browser console for warnings and errors. Runtime issues often show up here before they become visible in the UI.
  </Card>
  <Card title="Refresh When State Gets Stale" icon="rotate-right">
    If the preview looks wrong after many rapid changes, do a full refresh. HMR occasionally leaves stale state, especially after changes to context providers or routing.
  </Card>
</CardGroup>
